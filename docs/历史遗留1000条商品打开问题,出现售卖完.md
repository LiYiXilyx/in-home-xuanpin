# Temu 商品导航上下文异常与历史 1000 商品潜在遗留风险记录

版本：V1.0  
日期：2026-08-26  
项目：Temu 自动化选品系统  
适用阶段：Week1 商品池复核 / Day9 评论采集 / Catalog Scale V2

---

# 1. 文档目的

本文用于记录 Temu 商品在以下场景中出现的同类异常：

- 旧 `source_url` / `canonical_url` 直接打开显示 `sold out`
- 但从 Temu 站内当前商品卡点击进入后商品正常
- 同一 `goods_id` 在日常 Chrome 中可以搜索到
- 但在影刀控制的 Chrome / 另一个浏览器会话中显示 `No results`
- 类目页存在商品卡，但点击详情后仍可能 `sold out`
- 单次搜索失败并不能证明商品真实不存在

这些现象说明：

> Temu 商品详情、搜索结果和库存展示可能依赖当前浏览器会话、站内导航路径、Referral/Session 参数以及市场上下文。

因此系统不能把“旧 URL 可直接打开”或“单次搜索有结果”当作长期稳定事实。

---

# 2. 已确认的人工 A/B 现象

## 2.1 旧 URL 假 sold out

人工验证：

```text
A.
日常 Chrome
直接打开数据库保存的历史商品 URL
→ This item is sold out

B.
在 Temu 当前正常会话中：
首页
→ 摩托配件
→ 找到同一个 goods_id
→ 点击当前商品卡
→ 商品详情正常
```

结论：

```text
商品本身不一定真实售罄
```

更可能是：

```text
历史 URL / 旧 Referral / Session 上下文失效
```

## 2.2 搜索上下文差异

另一次人工 A/B：

```text
日常 Chrome
→ Temu 首页
→ 输入同一个 goods_id
→ 点击搜索
→ 有结果

影刀 Chrome
→ 同样从 Temu 首页搜索相同 goods_id
→ No results
```

这说明：

```text
同一 goods_id
+
不同浏览器会话 / Profile / Temu Context
=
可能得到不同搜索结果
```

不能把：

```text
No results
```

直接解释成：

```text
PRODUCT_NOT_FOUND
```

## 2.3 类目商品卡本身也可能过期

真实验证还发现：

```text
当前类目存在商品卡
↓
点击商品卡
↓
详情仍然 SOLD_OUT
```

因此不能只判断：

```text
找到商品卡
```

还必须继续验证：

- 详情页 `goods_id` 是否一致
- 页面是否可购买
- 评论区域是否存在
- 是否是真实可用详情

# 3. 当前根因判断

目前不能证明 Temu 内部具体使用了哪一种机制，因此不应把下面内容写成已确认事实。

但从真实 A/B 行为可以合理判断，异常与以下“导航上下文”因素高度相关：

- Chrome Profile
- Cookies
- LocalStorage
- Service Worker / Site Storage
- Temu 登录状态
- Germany / English / EUR 市场上下文
- Referral 参数
- Session 参数
- 站内跳转路径
- 搜索 Session
- 页面来源
- 浏览器启动方式
- 代理 / VPN / 网络出口

因此统一使用业务错误类型：

```text
NAVIGATION_CONTEXT_MISMATCH
```

而不是直接判断商品下架。

---

# 4. URL 语义修正

商品唯一身份必须始终保持：

```text
platform + goods_id
```

绝对不能改成 URL。

## 4.1 `source_url`

语义：

```text
historical navigation evidence
```

表示采集当时列表页看到的原始链接。

用途：

- 历史证据
- 调试
- fallback

不保证未来可以直接导航。

## 4.2 `canonical_url`

语义：

```text
stable compatibility reference
```

可以用于展示、记录和 fallback，但不能保证 Temu 当前 Session 下直接打开一定有效。

## 4.3 `fresh_url`

语义：

```text
current navigation resolution result
```

只表示当前这一次站内解析获得的有效导航地址。

不得覆盖商品稳定身份，也不得因为 `fresh_url` 改变而创建新的 product。

---

# 5. Fresh Navigation Resolver 正确流程

推荐顺序：

```text
claim-next
↓
goods_id
↓
CURRENT_CATEGORY_CARD
↓
找到当前商品卡
↓
点击
↓
详情验证
```

找不到：

```text
SITE_SEARCH_CARD
↓
搜索当前 goods_id
↓
找到商品卡
↓
点击
↓
详情验证
```

仍失败：

```text
重建 Temu 首页 / 搜索上下文
↓
重新搜索一次
```

仍失败：

```text
HISTORICAL_SOURCE_FALLBACK
↓
CANONICAL_FALLBACK
```

所有来源均失败后：

```text
NAVIGATION_NOT_RESOLVED
↓
人工复核
```

不得直接：

```text
PRODUCT_NOT_FOUND
```

---

# 6. 搜索失败的新处理原则

站内搜索出现 `No results` 只能表示本次搜索来源未解析成功，不能表示商品不存在。

建议状态：

```text
SEARCH_NO_RESULTS_TRANSIENT
SEARCH_CONTEXT_MISMATCH
NAVIGATION_NOT_RESOLVED
```

正式流程：

```text
第一次搜索 No results
↓
记录 SEARCH_NO_RESULTS_TRANSIENT
↓
回 Temu 首页
↓
重新建立搜索上下文
↓
确认 Germany / English / EUR
↓
再次搜索
↓
仍失败
→ 尝试其他导航来源
↓
仍失败
→ NAVIGATION_NOT_RESOLVED
```

---

# 7. 详情验证必须存在

无论来源是当前类目商品卡、站内搜索商品卡、历史 URL 还是 canonical fallback，都必须执行：

```text
page_goods_id === target_goods_id
```

同时检查 `detail_verified`，至少确认：

- 商品 ID 正确
- 不是错误商品
- 页面不是明显 sold out / invalid
- 存在购买区域或评论区域

只有 `FRESH_DETAIL_VERIFIED` 后，Browser Extension 才允许采集评论。

---

# 8. 推荐错误码

建议统一：

```text
STALE_OR_CONTEXT_BOUND_URL
NAVIGATION_CONTEXT_MISMATCH
SEARCH_CONTEXT_MISMATCH
SEARCH_NO_RESULTS_TRANSIENT
NAVIGATION_NOT_RESOLVED
FRESH_DETAIL_VERIFIED
```

不得把以下情况直接映射到 `PRODUCT_NOT_FOUND`：

- 历史 URL sold out
- 单次搜索 No results
- 当前类目没找到
- 当前商品卡点击后 sold out
- 影刀 Chrome 与日常 Chrome 结果不一致

---

# 9. 对第一周 1000 商品的潜在遗留风险

这是本次最重要的历史风险结论之一。

## 9.1 第一周 1000 条不代表全部错误

第一周商品池主要通过列表页采集，因此旧 1000 条可以拆成三层可信度：

### 第一层：商品身份

`goods_id` 可信度最高。只要当时商品卡解析正确，`goods_id` 仍然是最重要的历史资产。

### 第二层：列表页商品数据

包括：

- title
- price
- sales_count
- rating
- review_count
- image_url
- listing_rank

这些数据代表当次采集时页面看到的快照，仍然有历史价值。重新抓取时应该生成新 snapshot，而不是覆盖旧 snapshot。

### 第三层：导航状态

包括：

- `source_url`
- `canonical_url`
- `availability`
- 是否能直接打开详情
- 是否能通过搜索找到
- 是否可抓评论

这一层现在已经证明不能长期直接信任，因此需要重新验证。

---

# 10. 第一周可能埋下的问题是什么

不一定是“抓错了 1000 商品”。

更可能是当时存在一个隐含假设：

> 列表页保存的商品 URL 未来仍可以作为长期详情入口。

现在真实验证已经说明这个假设不可靠。

可能出现：

```text
Week1
商品卡正常
↓
保存 goods_id + source_url
↓
若干天后
直接复用 source_url
↓
sold out / no results
↓
错误怀疑商品下架
```

实际：

```text
通过当前 Temu 站内导航
↓
同 goods_id
↓
商品正常
```

因此第一周真正需要修正的是：

```text
Navigation Semantics
```

不是推翻：

```text
Product Identity
```

---

# 11. 为什么现在应该重新 Refresh 那 1000 条

重新抓 1000 的目的不是删除旧1000重新开始，而是：

```text
历史1000
+
当前重新验证1000
```

重新确认：

- 当前是否仍在类目中
- 当前 fresh 商品卡 URL
- 当前价格
- 当前销量
- 当前评分
- 当前评论数
- 当前排名
- 是否非电子
- 是否仍 business eligible
- 是否可进入详情
- 是否 reviewable
- 是否需要搜索 fallback

---

# 12. Refresh 1000 的正确数据处理

禁止：

```text
DELETE products
DELETE product_snapshots
DELETE reviews
```

正确：

```text
旧商品
↓
按 goods_id 匹配
↓
新增本轮 snapshot
↓
更新当前 membership / pool version
```

新商品：

```text
新增 products
+
snapshot
```

旧商品本轮没出现：

```text
not_seen_in_campaign
```

不能一次未出现就删除。

# 14. 如何判断第一周风险到底有多大

完成 Refresh 1000 后重点计算：

```text
历史URL异常率
=
historical_url异常商品数 / 旧1000
```

以及：

```text
Fresh Navigation恢复率
=
旧URL异常但fresh正常商品数
/
旧URL异常商品数
```

例如：

```text
旧1000中：
历史URL异常 = 220
Fresh Navigation恢复 = 190
```

则说明：

```text
goods_id / 商品身份大部分没有问题
```

真正问题是：

```text
历史URL不能长期复用
```

这会直接证明当前 Fresh Navigation 设计是必要的。

# 15. 对 3000 扩容计划的影响

不能简单：

```text
旧1000
+
新增2000
=
3000
```

因为这样会把旧1000中的导航风险直接继承到新池。

正确：

```text
旧1000
↓
Refresh / Re-validation
↓
形成新的1000基线
↓
1500
↓
2000
↓
2500
↓
3000
```

3000 Gate 应保证：

- `goods_id` 唯一
- 非电子
- 当前类目关系有效
- snapshot为新
- URL仅作历史证据
- Fresh Navigation机制可用
- reviewability有状态
- 不因单次 No results / sold out 错误删除商品

---

# 16. 浏览器环境差异必须记录

对于日常 Chrome 和影刀 Chrome，建议记录：

```text
browser_mode
profile_name
temu_logged_in
site_country
language
currency
navigation_method
source_page_url
search_key
result_count
```

不记录：

- Cookie 内容
- Token
- Secret
- 账号密码

目的只是判断同一个 `goods_id` 在不同运行环境下是否产生不同结果。

---

# 17. 影刀 RPA 的安全策略

影刀主要负责真实 Chrome 操作，包括：

- 首页导航
- 类目进入
- 搜索
- 滚动
- 商品卡点击
- CAPTCHA 人工关卡
- Extension触发

不要：

- 影刀自己判商品永久下架
- No results后立即跳过
- 旧URL直接作为首选
- 自动绕过验证码
- 直接写SQLite

Node / SQLite继续负责商品身份、状态、审计、去重、Queue 和 QA。

---

# 18. Browser Extension 的职责

Extension应该：

- 从当前页面读取 goods_id
- 确认 Context
- 提取评论
- 发送 localhost API

Extension不得：

- 因 URL 不同创建新商品
- 放宽 goods_id 校验
- 在 navigation 未 verify 时开始评论采集

已真实跑通：

```text

↓
Fresh Navigation
↓
navigation verify
↓
Context matched
↓
Extension
↓
localhost API
↓
SQLite
↓
```

因此本文件记录的问题不意味着 Fresh Navigation 失败。

> 正是这些真实异常证明 Fresh Navigation Resolver 必须存在。

# 20. 后续工程原则

后续所有 Temu 模块遵守：

1. `goods_id = identity`
2. `URL = evidence / navigation hint`
3. `No results != product not found`
4. `Sold out from historical URL != true sold out`
5. `Current card exists != verified detail available`
6. `Navigation must be verified before review capture`
7. `Historical data is retained, current state is refreshed`

# 22. 最终结论

目前证据支持的最稳妥结论是：

> 第一周的 1000 商品不应被整体判定为错误，但其中一部分商品的历史 URL、直接详情访问状态和后续评论可访问性可能受 Temu 导航上下文影响，因此存在“历史导航遗留风险”。

真正需要做的是：

```text
保留历史1000
↓
重新Refresh
↓
重新验证导航
↓
重新生成当前Pool
↓
再扩容3000
```

而不是：

```text
清空旧数据
↓
从零开始
```

这既保留历史资产，也可以利用新一轮数据量化第一周到底有多少商品受到 URL / Session / Navigation Context 影响。
